## Consulting Advisories (prioritised)

### 1. A PDF in a chat message can now kill the daemon — and the tool has no memory bound at all

`pdf_to_images` renders through `pdftoppm` at a **hardcoded `-r 200`**
(`src/utils/pdf_vision.rs`). On 2026-11-06 a Telegram message in a cowork chat carried a link to a
municipal zoning map; the agent fetched it and called the tool, and a single child reached
**946 048 kB anon-rss — 90.22 %** of the `opencrabs.service` cgroup's entire 1 GiB `MemoryMax`. The
kernel killed it, the service restarted into the same message, and the cycle ran **four times in
117 seconds** (`13:10:39Z`, `13:11:19Z`, `13:11:57Z`, `13:12:36Z`), leaving `NRestarts=4`.

Three separate facts make this worse than a one-off:

- **The resolution is not a parameter.** `-r 200` is a constant in the source. A caller who knows
  the document is large-format cannot ask for a cheaper render, because the tool's schema accepts
  only `path`, `pages` and `page_range`.
- **`BATCH_SIZE = 10` bounds pages, not area.** Ten A4 pages and ten A0 pages differ by roughly
  **100×** in raster memory and the batch size cannot see the difference.
- **On this host the bounded path does not exist.** The daemon logs
  `pdfium-render unavailable or failed: pdfium feature not enabled`, so every render takes the
  `pdftoppm` fallback — the one path with no other guard.

The kill takes the **whole daemon**, not the tool call, so one pasted map costs every other lane on
that profile its in-flight turn. Filed as **`leshchenko1979/opencrabs#814`** with the kernel lines,
the trigger timestamp and the proposed fix (DPI as a tool input, and bounding on estimated pixel
area rather than page count).

**This is the fleet's first user-reachable OOM.** Every prior OOM in the record came from a runaway
process or a test allocation. This one comes from a URL in a chat.

## Corrections to this artifact and to its predecessors

The artifact is a measurement, and a measurement that does not carry its own errors is a claim. Every
correction found while producing this round is recorded here, whether it was caught before the artifact
was written or after it was published.

**1. Yesterday's `AGENTS.md` share was printed as `64.49 %` when the same artifact had measured
`89.20 %`.** Two figures for one reading in one file, and the smaller one was carried into the summary
table while the larger sat in the detail. The real share is computed from the two sizes, not recalled:
`57 013 / 63 861 = 89.28 %` today. The error class is a **carried cell** — a number written once and
then restated from memory in a later table — and the remedy is that every table cell in this artifact
is computed in the same turn it is printed.

**2. Yesterday's Leg A percentage was computed against the wrong denominator.** Leg A is the always-loaded
set, not the whole brain directory; a share taken over every file in `profiles/ops/` understates each
file's weight in the per-turn context by exactly the on-demand files it adds. This round computes
`63 861 B` as the sum of the three always-loaded files alone and prints the composition beside it.

**3. Yesterday's Leg B count was a glob that did not match the profile's skill layout.** The skills live
under `skills/<skill>/SKILL.md` **and** under flat `skills/<name>.md`, and a single `*/SKILL.md` glob
sees only the first shape. Today's `36 skills / 6 960 lines` is enumerated over both, with the
per-skill line counts summed — a count read off an enumeration, never derived from a complement.

**4. Yesterday's advisory 10 (cron slot lateness) is WITHDRAWN as a trend claim.** It read a single
round's tight `+25 s` band as evidence of a stable phase. The same jobs' recent runs span the whole
0–60 s band, so the band is the tick's resolution and not the scheduler's behaviour. Today's `+58 s`
cohort is the same artefact in the opposite direction. Lateness stays printed; it is no longer read as
a movement.

**5. The memory overcommit figure was re-derived once and the correction was itself wrong.** Summing
`MemoryHigh` for both cgroups gave `241.57 %` of host memory; the first correction replaced it with a
