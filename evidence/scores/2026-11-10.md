### 5. The gate suite killed a daemon twelve times, and the mechanism is structural

Filed as **#638**. Twelve OOM kills in 14.55 min on `2026-11-09` (instants `14:43:06` …
`14:57:39`), one restart every 1.32 min, `NRestarts=12`, 54 `Killed process` lines over 44
distinct PIDs.

**The cgroup that died was `opencrabs.service`** — the DEFAULT-profile daemon, `MemoryMax`
**1 073 741 824 B = 1024 MiB**, `OOMPolicy=kill`, `ActiveEnterTimestamp`
`2026-11-09T14:57:44Z` (5 s after the last kill). It was **not** `opencrabs-ops.service`, which
reads `NRestarts=0` / `MemoryMax=3 221 225 472 B` / `OOMPolicy=continue` and whose
`ActiveEnterTimestamp` is `14:37:03Z`. `opencrabs-family.service` also reads `NRestarts=0`
(started `2026-11-04`, never restarted). **This correction matters for who can see it:** the
lane producing this artifact runs inside `opencrabs-ops.service`, a 3 GiB box, so its own runs
could never have reproduced the failure — which is exactly why the kill stayed invisible to the
instrument that was causing it.

Largest killed process: `python3`, pid `3115822` (non-commit: a kernel PID, not a git object),
**`anon-rss` 1 033 088 kB = 1008.875 MiB = 98.52 % of the 1024 MiB cap**, at
**`2026-11-09T14:47:35Z`**. A sibling reading of the same class
at the FIRST kill (`14:43:06`) is 996.79 MiB — the same failure at a different instant, and the
instant is named here because the figure is meaningless without it.

The mechanism: `tools/audit.py` re-execs under `systemd-run --user --scope` with its own
`MemoryMax` (the #600 mitigation), but `tools/gate_select.py` spawns gates with
`subprocess.Popen(..., start_new_session=True)` — and **`start_new_session` creates a session,
never a cgroup**. Verified with a positive control this round: a child spawned with that flag
reports `SAME CGROUP: True` while `session differs: True`. So every gate it runs is charged to
its caller's cgroup. `grep -ln systemd-run tools/*.py` returns exactly one file:
`tools/audit.py`. The ops daemon's caps were raised to 3072 MiB / 2816 MiB, which buys headroom
in the ops box and does not change the mechanism: any gate run is still unbounded within
whichever daemon's box it runs in — including the default profile's 1 GiB one.

**Measured vs inferred, stated:** the kills, caps, `OOMPolicy`, process names and RSS are
measured. That the killed `python3` was a gate run is **inferred** — consistent (1008.875 MiB
against a 1024 MiB cap; the suite's own measured peak was 1265.9 MiB on `2026-11-07`) but the
journal records the process, not its argv.
